# Implementation comparison with consolidated requirements

**Subsequent implementation status:** the user-approved conformance decisions are implemented in the [V1.1 conformance report](</D:/rohanjgeorge/SAP CoWork/sap-cowork/docs/V1_1_CONFORMANCE_DECISIONS_IMPLEMENTATION.md>). G01–G06 and G08–G11 are fixed; G07's retained compatibility fields and the current graph/profile composition are intentionally accepted. Explicitly excluded integrations remain deferred. The comparison below is the original read-only review snapshot, not a claim that these findings remain unfixed.

## Original review snapshot

Reviewed on 3 November 2026, Asia/Calcutta. This is a comparison for a decision, not an implementation change. The current working tree, including the earlier uncommitted updates, was reviewed. No application code, templates, dependencies or project data were changed.

**Conclusion:** The main SDLC workflow and technology choices are substantially aligned. There are six verified behavior gaps, two architectural differences, and three areas of partial coverage worth deciding on. Live SAP integration, enterprise identity, knowledge publication and several other capabilities are explicitly deferred by these documents; their absence should not be counted as a failure of the agreed local V1.1 baseline.

The documents also understate some work already present: native Context Planning, bounded Research, structured Audit and versioned artifact task profiles now exist in code. Their detailed engineering policies remain provisional, and real source integrations remain unconfigured.

## Verified behavior gaps

| ID / suggested priority | Document expectation | Actual implementation and observed difference | Decision needed |
| --- | --- | --- | --- |
| **G01 — High: mutation contract is inconsistent** | A §10; D §§4,15; O §8 require trusted actors, expected revisions and request IDs for public mutations. | The dedicated state-operation API requires revision/request IDs. Chat mutations make both optional; artifact editing requires a revision but no request ID; upload/delete paths do not expose the same complete mutation envelope. A POST changing Draft Stage without either value returned **200** and changed the stage. Internal state-service calls still serialize commits, but that does not reject a client's stale intent or deduplicate every request. See [API contracts](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/api.py:38>) and [state service](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/state_management.py:150>). | Require a consistent public mutation envelope, or explicitly document which client operations use weaker semantics. Keep authenticated actor identity server-owned. |
| **G02 — High: generation ID reuse does not compare payloads** | D §§4,15; O §§8,11 reject reuse of the same request identity with different parameters. | StateOperation IDs are signature-checked correctly. Generation uses completed task IDs differently: generating BRD, then retrying the same task ID with materially different instructions and a new-version request returned **replayed=true**, with the original single artifact. Only a changed artifact type is rejected. See [generation replay](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/langgraph_orchestrator.py:281>). | Bind generation identity to a normalized request signature and reject changed payloads; retain valid identical retries and saved-output recovery. |
| **G03 — High: blocker flags do not block execution** | O §3/§9 and A AP-10 require deterministic execution eligibility and active blocking-condition checks; D §3 defines blocker flags. | The guard checks `ProjectIssue.blocking`, but does not check active `Flag.type=blocker`. In the probe an active manual blocker flag remained active while a BRD was successfully generated. See [guardrail](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/hooks.py:22>) and [flag operations](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/state_management.py:423>). | Define which blocker flags prohibit which actions, and enforce them. Preserve the explicitly non-blocking ABAP/unapproved-TDD warning behavior. |
| **G04 — High: Testing completion does not require approved SIT/UAT** | O §5 explicitly lists approved SIT/UAT plus user-confirmed testing as the completion criterion; A §§4,12 require baseline-bound confirmations and strict closure. | `confirm_testing` checks that ABAP/SIT/UAT exist and stores their hashes, but does not require SIT/UAT approval. `stage_complete(Testing)` checks only the confirmation. With all three outputs still Draft, a testing confirmation was accepted and that helper returned **true**. Earlier missing prerequisites kept the probe's Approved Stage at Planning; closure still correctly requires current document approvals. See [completion criterion](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/state_management.py:57>) and [confirmation operation](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/state_management.py:441>). | Either require approvals when confirming, or allow a declaration first but keep Testing incomplete until approvals are present. Clarify whether a test-result reference is required beyond the current remarks/hash baseline. |
| **G05 — Medium: expected artifact can be absent on success** | O §§3,6,11 and A §17 require expected-output validation and successful structured Draft generation. | A replacement BRD capability returned `status=success` with no output. The task ended **completed**, no error was returned and no artifact existed. Invalid artifact bodies are rejected, but absence of the required artifact is accepted. See [validation hook](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/hooks.py:44>) and [completion path](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/langgraph_orchestrator.py:678>). | Validate the capability-specific expected output, while still allowing genuinely non-artifact tools to succeed without a document. |
| **G06 — Medium: package token cap is not always enforced** | A §8; O §4; T §4 require bounded context assembly. Exact limits remain engineering choices. | Passage selection removes evidence when it would exceed the cap, but metadata, gaps and final constraints can themselves exceed it. A valid configured cap of **1,000** produced a saved package estimated at **1,276** by the application's own estimator. Default-budget tests do not cover this case. See [package assembly](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/context_planning.py:755>). | Include all metadata in the bound, compact it or return an explicit insufficient-budget outcome. This is separate from choosing the final token threshold. |

## Architectural differences and partial coverage

| ID / classification | Document expectation | Current difference and practical implication | Suggested decision |
| --- | --- | --- | --- |
| **G07 — Architectural migration** | O §2 and Appendix A replace persisted task-status/wait authority with run-local LangGraph execution state. A §10 and D §3 allow some current-task projection. | ProjectState still persists `active_task_id`, `task_status`, active capability, task inputs and completed-task mappings. Generation, clarification and recovery consult these fields; after a generation graph ends, domain task status remains `awaiting_approval`. Checkpoints are reference-only and approval is already independent, so the original global approval wait is fixed. The remaining difference is runtime/domain coupling, not missing LangGraph. See [ProjectState](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/models.py:192>) and [runtime](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/langgraph_orchestrator.py:281>). | Decide whether to remove execution fields from canonical state, retain a clearly derived compatibility projection, and separately preserve durable idempotency/recovery records. This needs a schema migration and client compatibility plan. |
| **G08 — Architectural boundary** | D Appendix A and worker contracts call for only needed references/subsets rather than full ProjectState. | `CapabilityRequest.state` and `ArtifactGenerationRequest.relevant_state` still carry a full ProjectState object. The registry makes a deep copy, so a worker cannot mutate the parent's object through that reference. Artifact model prompts filter state fields; this finding does **not** mean the complete state is currently checkpointed or blindly sent to OpenAI. The worker-facing interface nevertheless remains broader than specified. See [envelopes](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/models.py:436>) and [worker adapter](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/artifact_worker.py:238>). | Introduce a compact immutable task view and explicit artifact/context references when the final contracts are agreed. |
| **G09 — Partial: SAP applicability and validity** | A §7; D §6; O §4 require claim-specific authority and unknown applicability to remain uncertainty. | Known mismatches are filtered, but `_mismatches` checks only target keys already populated. With an empty project SAP target and a synthetic registered adapter reporting S4P/release 2023, the release requirement was marked **satisfied**. Effective dates are stored but are not used as a validity filter in the planner. See [applicability](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/context_planning.py:611>) and [evaluation](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/context_planning.py:475>). A trusted project-bound connector could establish a target, but that binding is not an explicit contract today. | Decide whether target system/release must be supplied, derived from a trusted binding, or remain unconfirmed. Define effective-date validity before connecting real SAP systems. |
| **G10 — Partial: gap evidence and assumptions** | A §8; D §7; O §4 require actual attempted sources, unresolved reasons, follow-up, qualifications and assumptions. | Gap reasons, impacts, follow-up and provenance exist. However, ordinary gap entries derive `attempted_sources` from **all planned retrieval categories**, not per-requirement executed attempts; failures use adapter IDs instead. `ContextPackage.assumptions` exists but the current assembly path does not populate it. Gaps/qualifications therefore carry more information than the explicit assumptions list, and planned discovery can be mistaken for an actual attempt. See [gap construction](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/context_planning.py:562>) and [assembly](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/context_planning.py:755>). | Track requirement → executed action → evidence/failure consistently, distinguish planned/unattempted sources, and define how assumptions are extracted or declared. |
| **G11 — Partial: client metadata parity** | A §§1,3,17 and T §13 call for project/program linkage and shared UI/CLI lifecycle behavior. | The API and service accept program, organization, model policy and SAP applicability metadata. The project-creation UI and CLI expose only a subset; neither currently offers program/organization/SAP-target creation fields. Core generation/review/confirmation/withdrawal/closure work in both clients. See [API metadata](</D:/rohanjgeorge/SAP CoWork/sap-cowork/backend/app/api.py:27>), [project form](</D:/rohanjgeorge/SAP CoWork/sap-cowork/frontend/src/ProjectHome.tsx:17>) and [CLI creation](</D:/rohanjgeorge/SAP CoWork/sap-cowork/cli/main.py:95>). | Decide which metadata must be user-editable in each client, particularly if G09 requires a target binding. This does not require a new Program management subsystem. |

## Document status differs from current code

The source documents preserve a **1 November** implementation snapshot: 129 backend/CLI tests and 17 UI tests. Their status sections describe detailed Context Planning/Research/Audit implementation as deferred. That is useful historical context, but it is no longer a current inventory: the repository contains those subgraphs, profile files and their tests, and its latest recorded release gate reports **164 backend/CLI tests, 19 UI tests, four browser experience tests and the final STO scenario passing**. The recording completed at **01:37:42 on 3 November 2026, Asia/Calcutta**.

I inspected that evidence; I did not rerun the full release suite or overwrite its results during this review. Those tests demonstrate the covered scenarios, not full consolidated-requirement conformance. The targeted probes above show important cases that the passing suite does not currently reject.

The consolidated documents also settle two earlier interpretation issues in favor of current behavior: Draft changes normally update the current version, and `template_version` may hold the current template filename. Neither needs a new template registry or an automatic version bump merely to match this baseline.

## Decisions proposed for the next step

1. **Correct baseline behavior first:** agree G01–G06, then add acceptance tests for those cases and fix them without redesigning the clients. Keep non-blocking missing/unapproved inputs distinct from genuine execution blockers.
2. **Choose the state boundary deliberately:** decide G07/G08 before migrating persisted schemas or worker contracts. Removing task fields should preserve old projects, idempotency and registration recovery.
3. **Ratify evidence policies before real connectors:** settle target binding, effective dates, actual-attempt tracking, assumptions, and whole-task budget expectations in G09/G10.
4. **Choose client inputs and engineering contracts:** decide G11 and whether the current graph composition/profile dispatch is sufficient for this version.
5. **Keep deferred integrations separate:** select SAP connectors, enterprise IAM, Knowledge Management or production ABAP only as explicitly approved future scope.

No changes have been implemented as part of this comparison.
